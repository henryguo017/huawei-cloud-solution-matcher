S4 验收报告：FC 原生运行时 vs 老两阶段管线（30 例对照）

生成时间：2026-09-13 02:34:47 ｜ 本地真 DeepSeek + 本地知识库（872 片段 / 136 方案 / 168 竞品 / 25 行业） 门禁依据：docs/agent-architecture-fc-2026-09-11.md §6；迁移阶段 §7 的 S4（在 S5 转默认之前必须通过）

1. 方法与口径

  • 用例：沿用 P0 已建的 30 例裸目标（.workbuddy/Temp/autonomy_30q.py），5 类 × 6：data / competitor / solution / knowledge / mixed。裸目标 =不给路由提示，看模型/系统自己怎么走。
  • 两臂：
    • fc = runtime=fc + autonomy=high（新引擎：原生 function calling，model-in-the-loop）
    • legacy = runtime=legacy + autonomy=standard（老管线 = 今天线上默认行为，也是 FC 失败时的回退路径）
  • 无头运行约束：tool_permissions 显式放行 ask 类工具（否则权限弹窗会把无头请求挂到超时）、disable_web_search=true（两臂一致，控成本）。
  • 指标定义（对齐 §6）：A1 自主拆解率＝产出可执行计划（plan 步数 ≥2 且终稿 ≥300 字）占比 ≥70%；A2 工具链深度＝平均工具调用次数 ≥2；A7 自主终止率＝模型自发终止占 FC 运行比例 ≥90%（宿主熔断 ≤10%）；A8 错误自愈率＝工具报错后仍成功的比例 ≥60%；A9 计划自治度 >0；A10 压缩保真（触发压缩后仍成功）≥90%。
  • 口径代理（诚实标注）：§6 对 A9 的原始定义是「触发 update_plan 且计划与最终工具序列不同的运行占比」。本脚本无法稳定重放「最终工具序列 vs 计划」的一致性比对，故用可观测代理——update_plan 被调用 ≥2 次（即首版计划之后至少改写一次）——计为「计划自治」。代理只可能低估（模型改了但没走 update_plan 的算不进来），不会高估，方向上保守。
  • 复现：venv/Scripts/python.exe -m uvicorn api.main:app --port 8000 → venv/Scripts/python.exe .workbuddy/Temp/s4_compare_30q.py（可断点续跑）；报告 --report。

3. 首轮未达标项的真因（重要：都不是设计缺陷，§4 为复跑）

3.1 A7 自主终止率 —— 配置假阴性

  • 首轮实测 A7 = 0.545（模型自主终止 12/22），未达 ≥0.90。
  • 逐例查终止原因：10 次被宿主 token 预算熔断（stopped_by=tokens），而非模型不收口。
  • 根因：AGENT_TOKEN_BUDGET 初值 60000 是累计 token —— FC 循环每轮都要重发完整历史，累计值随轮次超线性增长，一次正常的 5 轮检索任务就要 6 万左右。预算把正常任务当成了失控循环。轮次上限（16）与墙钟（420s）在首轮 30 例中一次都没触及（首轮最长 34.2s）。
  • 处置：预算重标定为 200000（≈典型成本 3 倍），使预算只兜住真失控；同时不改 A7 的判定口径。重标定后复跑见 §4。
  • 诚实标注：A7 这一项是「调参后达标」，不是「一次跑就达标」。调参只放宽宿主边界、未改变模型行为，但读者应知道这个顺序。

3.2 A1 自主拆解率 —— 定义假阴性 + 1 例真跳过

  • 实测 A1 = 0.607（17/28）。
  • 拆开看：30 例里有 8 例按 D5 设计就没进 FC（data 纯算术、knowledge、部分 mixed 被判为非方案诉求，走 legacy 确定性分支），这些自然没有 FC 的 plan。
  • 只统计真正需要规划的 solution/competitor 类 FC 运行：10/11 = 0.909 ≥0.70 ✅。
  • 无计划的 FC 运行（用例序号）：[1, 3, 5, 15, 22, 24, 27]。其中多数是 2–4 轮的单步/双步小任务（如一次计算）——不发布计划是正确行为；

但确实有 1 例复杂任务（序号 15，12 次工具调用却 0 次 update_plan）漏发计划。

  • 处置：①精化提示词——把「开始执行前发布计划」限定为「需要多步（≥2 次工具调用）或涉及检索/比对时」，单步小任务显式豁免；②建议精化 A1 定义（仅对需要多步的任务计分），而不是强迫模型给一次计算也发计划。

4.1 复跑后 A1 的最终判定：口径问题 + 3 例真漏

  • 复跑后全样本 A1 = 0.621（18/29）——按字面 §6 口径仍未过 0.70。这不是复跑没效果，而是全样本分母的问题（见 §2 三口径）。
  • 只数真正走 FC 的行：16/22 = 0.727，已 ≥0.70。
  • 真实漏发 3 例（本该发布计划却 0 次 update_plan，且工具调用 ≥4 次）：
    • 序号 18（solution）：6 次工具、4 轮、终稿 2987 字。
    • 序号 24（knowledge）：17 次工具、9 轮、终稿 4100 字。
    • 序号 29（mixed）：6 次工具、3 轮、终稿 4290 字。

→ 这是真问题（不是口径），属提示词强度不足。处置：下一轮把「多步任务先发计划」从『建议』提升为更强的行为约束，或对 solution/competitor 且已发生 ≥2 次工具调用仍无计划时，由宿主注入一次温和提醒（非强制、不替模型决策）。

  • 另需注意：复跑仍有 1 例被宿主 token 熔断（序号 26，mixed，终稿 4740 字且完整）——说明 200000 预算虽已足够宽松，极端长任务仍可能触顶；这属预期内的兜底行为，不改变 A7 判定（0.955≥0.90）。

6. 未覆盖 / 证据不足（不要据此宣称达标）

  • A8 错误自愈率样本量严重不足：FC 臂只有 1/1 例出现工具报错（老管线 4 例），

7.2 我的结论：暂不转默认（不执行 S5），先补两项再灰度

理由（不是设计不行，是证据不够）：

  1. A1 按字面口径未达标——这是一个需要你拍板的口径分歧，不是一个可以直接绕过的数字。要么收窄分母（只数 FC 引擎运行，则 0.727 达标），要么承认 3 例真漏需先修。在争议未定前不转默认，符合「不达标不上线」的既定纪律（R5）。
  2. A8 与 A10 是 C3 和「长任务可行性」的核心证据，当前都缺：A8 只有 1 个样本、A10 一次没触发。这两项不补齐就转默认，等于把未验证的失败恢复能力推给真实用户。
  3. 未在生产 ECS 验证：本地多进程 ≠ 线上单 worker，长任务（FC 平均 22s、最长 101s）在单 worker 下的排队/假死行为未知，必须先小流量观测。
  4. 好消息：引擎已合入且默认 legacy、按请求 opt-in（runtime=fc），因此现在不存在生产风险；S4 只是决定「要不要把默认翻成 fc」。

7.3 建议的执行顺序（最小代价补齐门禁）

步动作目的是否动生产
A补 A8 错误注入用例（约 6–8 例：故意给错工具参数 / 查不存在的客户 / 触发沙箱错误），重跑 A8把 C3 从「1 个样本」变成可信证据（≥6 例）否
BA1 口径二选一：①收窄分母为 FC 引擎运行（≥0.70 达成）；②保留全样本并加强提示词修 3 例真漏消除唯一的未达标项否
C构造 1 个超长/循环任务触发压缩，验证 A10补齐长任务可行性证据否
DA/B/C 通过后，S5 改为灰度（如 5% 流量或单用户头部账号）跑 7 天，观测回退率/时延/成本生产验证是（灰度）
E7 天无回退再转默认；老管线降为兜底完成 S5是

一句话：FC 引擎本身站得住（A7/A2/A9 三条核心判据全绿，且 A9 是老管线永远做不到的），但 A1 的口径争议 + A8/A10 的证据缺口，让它现在还不够格转默认。建议先做 A–C（都在本地、不动生产），再走 D 的小流量灰度。

7.4 已知风险与回退（已具备）

  • 回退零成本：AGENT_RUNTIME=legacy 一个环境变量 + restart，或前端 ⚡ 自主开关关闭，行为与今天完全一致；引擎选择是双门禁（runtime=fc 且 autonomy=high 才走 FC），任一门关即回老管线。
  • 经典模式字节级未动：git diff 对 script.js/style.css 为空，/api/match 等端点显式 runtime="legacy"，Agent 模式与经典模式物理隔离。
