1. 定位：两层都要 —— 通用底座 + 垂直售前包

目标是完全自主的售前 Agent：不是"能力面铺得很宽的通用助手"，也不是"只能按固定流程跑的脚本"。 落地形态是双层：

层是什么与行业的关系
通用底座自主循环、计划/待办机制、子体派生、记忆 API、工具注册与自扩展、守卫与审计行业无关。换包即另一个垂直
垂直售前包售前资产、售前工具、售前角色子体、售前阶段语义只服务售前

判据：自主度是手段，售前闭环是本体。 一个任务从线索到交付物 + 推进建议，全程不需要人喂下一步。

自主度阶梯（现状 → 目标）

档特征位置

4. P0 详细设计（计划绑定）—— 已实现

4.1 语义变更

计划从叙述性（给用户看的进度视图，明确"不约束执行"）改为有齿的待办：

  • 终稿交付前，计划里每一步必须闭合：done，或 skipped（必须带原因）。
  • 有未闭合项时，宿主不接收终稿，把未闭合项退回给模型，由模型自决：补做，或如实标 skipped。
  • 新增 skipped 状态 = 允许放弃，但必须显式声明——不允许"默默不收尾"。

4.2 边界纪律（这不是宿主夺权）

宿主只做一件事：查「模型自己发布的计划有没有未闭合项」这一个事实。然后给模型两个选项。

宿主不做：

  • ❌ "某工具属于哪一步"的归属推导（那正是架构文档 §8 要删的 _tool_to_plan_index）
  • ❌ 规定执行顺序（顺序仍完全由模型决定）
  • ❌ 替模型决定补做还是跳过

4.3 实现清单

4.4 防死锁

最多交回 AGENT_PLAN_CLOSE_MAX_RETRY（默认 2）次；超出则接受终稿并打告警标记—— 原则：宁可告警，不可卡死。代价：仅在发生漂移时多 1–2 次 LLM 调用。

5.1 P1 实现记录（2026-09-13）

为什么不能直接删掉那道 if。 旧实现 if _fc_kind in ("solution", "competitor") 是一道内容门：用意图分类结果决定"这个需求配不配进自主循环"。它存在的唯一原因是政策提示词是静态的——POLICY_PROMPT 写死了售前方案姿态（「客户痛点→华为云方案→实施路径→价值收益，1500-3500 字」）。若不改政策就放开意图，会立刻重犯 2026-09-09 的线上实锤 bug：问"你会玩王者荣耀吗？"产出 14 章游戏行业方案书。

正解：把门从"内容判断"降级为"路径判断"，姿态改由意图切换。

层旧新
是否进 FC意图 ∈ {solution, competitor}意图 ∉ {greeting, account, export}（context.fc_takes_over）
写成什么样恒定方案契约build_policy_prompt(intent) 按意图出契约（_CONTRACTS）
通用部分与契约混在一个字符串里_AUTONOMY_BLOCK（自主性 + 计划机制 + 工作准则 8 条）恒定注入

排除 greeting/account/export 的理由（它们是路径问题，不是内容问题）：

  • greeting：礼节寒暄，legacy 有模板直答，进 FC 只是白烧一次 LLM 调用；
  • account：账户信息查询，确定性查库，不需要模型自主规划；
  • export：导出是一次确定性文件动作（绑 _last_draft），不该由模型即兴发挥。

抗分类偏差兜底。 分类器本身有已知偏差（实测 30 题里「50 台 4核8G 服务器每台月费 380 元…」被规模词截进 solution、「帮我为一家连锁药店做数字化转型的方案框架」落 general）。因为放开门之后分类错误不再决定"是否自主"、只影响"姿态"，所以通用块加了一条：「交付姿态以用户实际诉求为准……你的判断优先于预判」 —— 模型读得到原文，理应有最终发言权。

收口重试（兜底，非主因）。 收口调用改为重试一次（仍空才判失败），并在失败时把真实运行态写进 fc_meta，使"从未进 FC"与"进了但失败"可区分。注意：当时把 27% 硬回退归因于"收口返回空 content"，此判断已被 §5.2 证伪——真因是 thinking 模式的 reasoning_content 回传硬校验，与收口无关。

回退：AGENT_RUNTIME=legacy / 前端 ⚡ 开关（代码层零改动）；预算分档可用 env 覆盖（AGENT_TOKEN_BUDGET_SOLUTION / _COMPETITOR）。

5.2 真因定位：reasoning_content 回传硬校验（2026-09-13 收尾）

现象。 P1 放开范围门后跑 30 例，出现 8 例 FC 硬回退（run_loop_none）：FC 尝试 30（成功 22 / 失败回退 8）。特征是间歇的——同一 query 重跑常成功（8 例里 6 例重跑正常），只有 #9/#29 曾连续复现，且随后又自愈。

排除法与证据链。

步骤做法结果
① 找异常出口发现旧代码所有失败路径只走 harness._log（受 verbose 门控不落盘）→ 磁盘上完全不可见加独立 logger.warning 出口
② 定位到 HTTP 层服务日志出现成对的 HTTP/1.1 400 Bad Request（2 次 = MAX_RETRIES=2，间隔 2s）400 属请求侧错误，重试纯属浪费
③ 穷举消息形状9 种可疑形状打真实 DeepSeek（.workbuddy/Temp/llm_400_probe.py）只有「孤儿 tool_calls / 回填不足」会 400 —— 但生产形状签名（T16 检测器）显示回填是足的
④ 抓到响应正文主循环 WARNING 落盘，拿到真实 bodyThe reasoning_content in the thinking mode must be passed back to the API.
⑤ 确定规则边界.workbuddy/Temp/reasoning_probe*.py：thinking 开/关 × 历史是否带该字段见下表

规则（实测，非文档推断）：

场景结果
thinking=enabled + 历史 assistant 缺 reasoning_content 字段❌ 400
thinking=enabled + 历史 assistant 有该字段（值为空串）✅ 200
thinking=enabled + 历史 assistant 有真实推理✅ 200
thinking=disabled + 历史带/不带该字段✅ 均 200
thinking=enabled + 一段有、一段缺字段（混合）❌ 400

结论：该字段必须"在场"，值可为空串。 本项目 to_assistant_message 只保留 content/tool_calls，把 reasoning_content 剥掉了 → 决策轮（AGENT_THINKING_DECISION=enabled）进入第 2 轮起就可能 400。

为什么间歇。 轮次 thinking 分档是 plan_all_done ? FINAL(disabled) : DECISION(enabled)；plan_all_done 会在任何工具调用后复位为 False。于是出现「disabled 轮写入了一条不带 reasoning 的 assistant → 下一轮又回到 enabled」的混合历史 → 400。走不走得到这个序列取决于模型是否恰好在"计划全闭合"那轮还调工具，故表现为间歇。

修复（三处，均为最小改动）：

文件改动
runtime/schema.py to_assistant_message新增 reasoning_content 参数并恒置该键（有真实推理传真实值，否则空串）；不编造内容
runtime/schema.py sanitize_messages保留并兜底补齐 reasoning_content（原实现重建 assistant 消息时会把它丢掉，等于修复被抹掉）
runtime/runner.py两处 assistant 入栈（工具轮 / 计划闭合门拦截轮）传入 reasoning

顺带修掉的真实缺陷（models/llm.py）：

  • _retry_request 是 except Exception 宽口重试器，会把 chat_with_tools 为 4xx 抛出的 RuntimeError 无差别重试 —— 与该方法文档承诺的"4xx 不重试"完全相反，每次非法请求白烧 2s + 2 倍计费。
  • 修复：新增 NonRetryableLLMError + _is_retryable()（鸭子类型读 response.status_code，兼容 provider 包装层），4xx / 显式不可重试异常立即抛出；5xx / 429 / 传输超时保持原有重试。

新增诊断设施（排障资产，非业务逻辑）：

  • schema.message_shape(messages)：把消息序列压成一行形状签名（system,user,assistant+tc(2),tool,tool），并标记 !!orphan_tool_calls@[idx]。用于定位 400 唯一的结构性成因，可安全落盘（不含正文）。
  • runner 主循环 catch 与收口失败路径各加一条 logger.warning 落盘诊断（含 turn/thinking/msgs/safe_len/shape/err）；safe_len 用于发现 sanitize_messages 丢消息。
  • fc_meta 现含更具体 reason（llm_error / no_draft_after_close）与形状签名。

验证。 离线套件 98/98（新增 T15 重试策略、T16 形状检测器、T17 reasoning 直通）；本地回归门禁 100/100 意图 + 16/16 沙箱 PASS。活测复验见 §5.3。
