## 1. 定位：两层都要 —— 通用底座 + 垂直售前包

目标是**完全自主的售前 Agent**：不是"能力面铺得很宽的通用助手"，也不是"只能按固定流程跑的脚本"。
落地形态是**双层**：

| 层 | 是什么 | 与行业的关系 |
|---|---|---|
| **通用底座** | 自主循环、计划/待办机制、子体派生、记忆 API、工具注册与自扩展、守卫与审计 | **行业无关**。换包即另一个垂直 |
| **垂直售前包** | 售前资产、售前工具、售前角色子体、售前阶段语义 | **只服务售前** |

**判据：自主度是手段，售前闭环是本体。** 一个任务从线索到交付物 + 推进建议，全程不需要人喂下一步。

### 自主度阶梯（现状 → 目标）

| 档 | 特征 | 位置 |
|---|---|---|
| L0 流水线 | 宿主写死步骤（legacy 两阶段，今天线上默认） | — |
| **L1 模型选工具** | 仅 `solution`/`competitor` 进循环；短程（均 5 轮）；计划**不绑定** | **← 现状（S4 验证到此）** |
| L2 计划绑定 + 全意图 | 计划成为有齿的待办；所有意图进循环 | 目标 P0/P1 |
| L3 长程自愈 | 压缩后续跑；错误自愈；自写记忆 | 目标 P2 |
| L4 自扩展委派 | 自建工具/技能；派生子 agent；按需挂 MCP | 目标 P3 |

## 3. 双层边界（什么属于哪一层）

| 能力 | 归属层 | 理由 |
|---|---|---|
| 自主循环 / 终止判定 / 预算熔断 | 通用底座 | 与任务内容无关 |

| 子体派生、记忆读写 API、工具注册与自扩展 | 通用底座 | 引擎能力 |
| **售前阶段语义**（客户画像→需求识别→方案匹配→竞品对标→报价/TCO→交付物+跟进） | **垂直包** | 由包注入默认骨架，模型可改写 |

## 4. P0 详细设计（计划绑定）—— 已实现

### 4.1 语义变更

计划从**叙述性**（给用户看的进度视图，明确"不约束执行"）改为**有齿的待办**：

- 终稿交付前，计划里**每一步必须闭合**：`done`，或 `skipped`（**必须带原因**）。
- 有未闭合项时，宿主**不接收终稿**，把未闭合项退回给模型，由模型自决：**补做**，或**如实标 skipped**。
- 新增 `skipped` 状态 = 允许放弃，但必须**显式声明**——不允许"默默不收尾"。

### 4.2 边界纪律（这不是宿主夺权）

宿主**只做一件事**：查「模型自己发布的计划有没有未闭合项」这一个事实。然后给模型**两个选项**。

宿主**不做**：
- ❌ "某工具属于哪一步"的归属推导（那正是架构文档 §8 要删的 `_tool_to_plan_index`）
- ❌ 规定执行顺序（顺序仍完全由模型决定）
- ❌ 替模型决定补做还是跳过

### 4.3 实现清单

| 文件 | 改动 |
|---|---|
| `app/config.py` | `AGENT_PLAN_CLOSE_ENFORCE=1`、`AGENT_PLAN_CLOSE_MAX_RETRY=2` |
| `app/agent/runtime/todo.py` | 状态词表加 `skipped` 及近义词；schema 描述改为"待办 + 收尾前须闭合"；新增 `open_steps()` / `closure_summary()` / `build_close_instruction()` |
| `app/agent/runtime/runner.py` | 终稿分支加**闭合门**：未闭合且未达上限 → 注入交回提示并 `continue`；`plan_all_done` 改为**闭合**判定（done/skipped）；`trace.plan_drift_rejections` 计数 |
| `app/agent/runtime/context.py` | POLICY 两条硬性要求：①连续工具调用 ≥2 次无计划必须补发；②**交付前计划必须闭合**，禁止虚标 done |
| `app/agent/harness.py` | `fc_meta` 增 `drift_rejections` / `plan_open_at_final` |

### 4.4 防死锁

最多交回 `AGENT_PLAN_CLOSE_MAX_RETRY`（默认 2）次；超出则**接受终稿并打告警标记**——
原则：**宁可告警，不可卡死**。代价：仅在发生漂移时多 1–2 次 LLM 调用。

### 4.5 验收

- **离线**：`.workbuddy/Temp/fc_runtime_smoke.py` **44/44 通过**（新增 8 项 P0 检查）
  - `T10` 计划留 1 步未闭合 → 断言：拦截 1 次、模型改为 `skipped` 后交付、共 5 次 LLM 调用
  - `T10b` 模型死不闭合 → 断言：拦截恰为上限 2 次、**仍产出终稿**（不死锁）
  - 附带验证：计划全闭合后 thinking 自动降档（`enabled → disabled`），证明 `skipped` 被正确当作闭合信号
- **新增指标 A11 计划收敛率** = 交付时计划全闭合的运行 / 发布过计划的 FC 运行，目标 **≥0.90**
- **待办**：本地活测（需拉起重启服务）——给一个多步售前任务，确认出现「模型**自己**发现漏步并补上」的行为，而不是靠改提示词

### 4.6 回退

`AGENT_PLAN_CLOSE_ENFORCE=0` + restart → 行为回到今天。**经典模式与 legacy 管线一行未动。**

### 5.1 P1 实现记录（2026-09-13）

**为什么不能直接删掉那道 `if`。** 旧实现 `if _fc_kind in ("solution", "competitor")` 是一道**内容门**：用意图分类结果决定"这个需求配不配进自主循环"。它存在的唯一原因是**政策提示词是静态的**——`POLICY_PROMPT` 写死了售前方案姿态（「客户痛点→华为云方案→实施路径→价值收益，1500-3500 字」）。若不改政策就放开意图，会立刻重犯 2026-09-09 的线上实锤 bug：问"你会玩王者荣耀吗？"产出 14 章游戏行业方案书。

**正解：把门从"内容判断"降级为"路径判断"，姿态改由意图切换。**

| 层 | 旧 | 新 |
|---|---|---|
| 是否进 FC | 意图 ∈ {solution, competitor} | 意图 ∉ {greeting, account, export}（`context.fc_takes_over`） |
| 写成什么样 | 恒定方案契约 | `build_policy_prompt(intent)` 按意图出契约（`_CONTRACTS`） |
| 通用部分 | 与契约混在一个字符串里 | `_AUTONOMY_BLOCK`（自主性 + 计划机制 + 工作准则 8 条）恒定注入 |

**排除 greeting/account/export 的理由**（它们是路径问题，不是内容问题）：
- `greeting`：礼节寒暄，legacy 有模板直答，进 FC 只是白烧一次 LLM 调用；
- `account`：账户信息查询，确定性查库，不需要模型自主规划；
- `export`：导出是一次**确定性文件动作**（绑 `_last_draft`），不该由模型即兴发挥。

**抗分类偏差兜底。** 分类器本身有已知偏差（实测 30 题里「50 台 4核8G 服务器每台月费 380 元…」被规模词截进 `solution`、「帮我为一家连锁药店做数字化转型的方案框架」落 `general`）。因为放开门之后分类错误不再决定"是否自主"、只影响"姿态"，所以通用块加了一条：**「交付姿态以用户实际诉求为准……你的判断优先于预判」** —— 模型读得到原文，理应有最终发言权。

**收口重试（兜底，非主因）。** 收口调用改为**重试一次**（仍空才判失败），并在失败时把真实运行态写进 `fc_meta`，使"从未进 FC"与"进了但失败"可区分。**注意**：当时把 27% 硬回退归因于"收口返回空 content"，此判断已被 §5.2 证伪——真因是 thinking 模式的 `reasoning_content` 回传硬校验，与收口无关。

**回退**：`AGENT_RUNTIME=legacy` / 前端 ⚡ 开关（代码层零改动）；预算分档可用 env 覆盖（`AGENT_TOKEN_BUDGET_SOLUTION` / `_COMPETITOR`）。

### 5.2 真因定位：`reasoning_content` 回传硬校验（2026-09-13 收尾）

**现象。** P1 放开范围门后跑 30 例，出现 8 例 FC 硬回退（`run_loop_none`）：`FC 尝试 30（成功 22 / 失败回退 8）`。特征是**间歇的**——同一 query 重跑常成功（8 例里 6 例重跑正常），只有 #9/#29 曾连续复现，且随后又自愈。

**排除法与证据链。**

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① 找异常出口 | 发现旧代码所有失败路径只走 `harness._log`（受 `verbose` 门控**不落盘**）→ 磁盘上完全不可见 | 加独立 `logger.warning` 出口 |
| ② 定位到 HTTP 层 | 服务日志出现成对的 `HTTP/1.1 400 Bad Request`（2 次 = `MAX_RETRIES=2`，间隔 2s） | 400 属**请求侧**错误，重试纯属浪费 |
| ③ 穷举消息形状 | 9 种可疑形状打真实 DeepSeek（`.workbuddy/Temp/llm_400_probe.py`） | 只有「孤儿 tool_calls / 回填不足」会 400 —— 但生产形状签名（T16 检测器）显示**回填是足的** |
| ④ 抓到响应正文 | 主循环 WARNING 落盘，拿到真实 body | **`The reasoning_content in the thinking mode must be passed back to the API.`** |
| ⑤ 确定规则边界 | `.workbuddy/Temp/reasoning_probe*.py`：thinking 开/关 × 历史是否带该字段 | 见下表 |

**规则（实测，非文档推断）：**

| 场景 | 结果 |
|---|---|
| `thinking=enabled` + 历史 assistant **缺** `reasoning_content` 字段 | ❌ 400 |
| `thinking=enabled` + 历史 assistant 有该字段（值为**空串**） | ✅ 200 |
| `thinking=enabled` + 历史 assistant 有真实推理 | ✅ 200 |
| `thinking=disabled` + 历史带/不带该字段 | ✅ 均 200 |
| `thinking=enabled` + 一段有、一段缺字段（混合） | ❌ 400 |

**结论：该字段必须"在场"，值可为空串。** 本项目 `to_assistant_message` 只保留 `content`/`tool_calls`，把 `reasoning_content` 剥掉了 → 决策轮（`AGENT_THINKING_DECISION=enabled`）进入第 2 轮起就可能 400。

**为什么间歇。** 轮次 thinking 分档是 `plan_all_done ? FINAL(disabled) : DECISION(enabled)`；`plan_all_done` 会在任何工具调用后复位为 False。于是出现「disabled 轮写入了一条不带 reasoning 的 assistant → 下一轮又回到 enabled」的混合历史 → 400。走不走得到这个序列取决于模型是否恰好在"计划全闭合"那轮还调工具，故表现为间歇。

**修复（三处，均为最小改动）：**

| 文件 | 改动 |
|---|---|
| `runtime/schema.py` `to_assistant_message` | 新增 `reasoning_content` 参数并**恒置该键**（有真实推理传真实值，否则空串）；不编造内容 |
| `runtime/schema.py` `sanitize_messages` | 保留并兜底补齐 `reasoning_content`（原实现重建 assistant 消息时会把它丢掉，等于修复被抹掉） |
| `runtime/runner.py` | 两处 assistant 入栈（工具轮 / 计划闭合门拦截轮）传入 `reasoning` |

**顺带修掉的真实缺陷（`models/llm.py`）：**

- `_retry_request` 是 `except Exception` 宽口重试器，会把 `chat_with_tools` 为 4xx 抛出的 `RuntimeError` **无差别重试** —— 与该方法文档承诺的"4xx 不重试"完全相反，每次非法请求白烧 2s + 2 倍计费。
- 修复：新增 `NonRetryableLLMError` + `_is_retryable()`（**鸭子类型**读 `response.status_code`，兼容 provider 包装层），4xx / 显式不可重试异常立即抛出；5xx / 429 / 传输超时保持原有重试。

**新增诊断设施（排障资产，非业务逻辑）：**

- `schema.message_shape(messages)`：把消息序列压成一行形状签名（`system,user,assistant+tc(2),tool,tool`），并标记 `!!orphan_tool_calls@[idx]`。用于定位 400 唯一的结构性成因，可安全落盘（不含正文）。
- `runner` 主循环 catch 与收口失败路径各加一条 `logger.warning` 落盘诊断（含 `turn/thinking/msgs/safe_len/shape/err`）；`safe_len` 用于发现 `sanitize_messages` 丢消息。
- `fc_meta` 现含更具体 `reason`（`llm_error` / `no_draft_after_close`）与形状签名。

**验证。** 离线套件 98/98（新增 T15 重试策略、T16 形状检测器、T17 reasoning 直通）；本地回归门禁 100/100 意图 + 16/16 沙箱 PASS。活测复验见 §5.3。
