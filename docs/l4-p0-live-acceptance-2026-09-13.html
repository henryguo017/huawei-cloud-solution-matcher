4. 活测发现并已修复的缺口：熔断路径绕过闭合门

问题：熔断（预算/轮次到顶）走的是「宿主索要终稿」分支，该分支此前不经过闭合门 → 模型可能带着未闭合步直接出终稿，且宣称已完成。

修法（app/agent/runtime/runner.py，提交 3b872b0）：熔断收口时若 open_steps(harness._plan_status) 非空，则在收口指令后追加：

（宿主补充）注意：你计划里仍有未闭合的步骤（…）。本次因预算/轮次已到上限无法继续执行，请务必在答案中如实说明哪些部分尚未完成或未核实，不要谎称已经完成。

边界（关键）：不改 A11 口径（该样本如实算失败）、不改执行顺序、不做「工具属于哪一步」的步归属推导 —— 宿主只做核验，不替模型粉饰。

验证：

  • 离线：fc_runtime_smoke.py 48/48（新增 T10c 断言注入文本 + 终稿如实说明；T10b 断言超限后不死锁）。
  • 活测：定向探针 .workbuddy/Temp/p0_fuse_probe.py 复跑同题 → stopped_by=tokens + plan_open_at_final=2 → 终稿出现「七、待补充与未核实事项（如实说明）」小节，列出 4 条真实缺口（联网通道关闭 / 未调成本工具 / 未写入客户档案 / 阿里云侧颗粒度弱）。逻辑闭环：熔断 + open>0 ⟹ 必然注入。

6.2 关键观察

  1. 曾经的失败样本（#7，制造业物联网竞品对比）这次跑完了 —— 12 轮 / 17 次工具调用 / 316,417 tokens，模型自主终止、计划全闭合。它正是上一轮在 200k 被掐断的那一例。熔断根因确认为预算过紧，非模型能力。

6.3 预算定档（数据驱动）

AGENT_TOKEN_BUDGET：200000 → 500000。

依据值
实测峰值（#7）316,417
轮次上限推算（16 轮 × 实测 ~26k/轮）≈ 420,000
选定值500,000（高于峰值 58%，对齐轮次上限）

设计意图：让轮次（AGENT_MAX_TURNS=16）成为真正的约束，token 预算退化为「只兜住病态单轮膨胀」的最后一道闸 —— 这样熔断行为可预测，不会再随机掐断正常长任务。

备注：本次复验在 400k 下已完成且 0 熔断（模型在 ≤316k 处自行停手）；升到 500k 只是把天花板抬到必然高于任何合法运行，无需重复消耗复验 —— 模型自主终止的样本不受天花板抬高影响。

7. 结论与后续选项

  • ✅ P0 目标达成：计划从「叙述性」变成「有齿的待办」，且齿是模型自己咬合的 —— 扩测后 A11 主口径 1.000（8/8），样本充足时宿主无需介入（0 次拦截）。
  • ✅ 熔断根因已消除：A11 首轮 0.750 的唯一失败＝预算过紧掐断长任务；已重标定 200k → 500k，扩测 0 熔断。曾经的失败样本（#7）在放宽预算后跑完全程并自主闭合。
  • ⚠️ 当时仍未做的（已在 §8 全部关闭）：① 样本仍限于 solution/competitor 两类意图（范围门未开，属 P1）；② 4 例分流 legacy 的样本不计入 A11，故 A11 尚未覆盖全部意图；③ 天花板抬到 500k 后需留意账单。
  • 可选后续（未做，供决策）：
    • 按意图分档：实测 solution ≤95k、competitor ≤316k，两档差异显著。若要收紧成本，可让 solution 用 200k、competitor 用 500k（run_loop 可直读 harness._intent，无需改函数签名）。当前取单一 500k 是为少一条代码路径、行为可预测 —— 代价是轻量任务也拿到高天花板。
    • (b) 熔断时若计划未闭合则有界延期（须防死锁）—— 在预算已不轻易触发的前提下优先级下降。
  • 回退：AGENT_TOKEN_BUDGET=200000（回到旧档）；AGENT_PLAN_CLOSE_ENFORCE=0（闭合门整体关）；FC 本身仍可用 AGENT_RUNTIME=legacy 或前端 ⚡ 开关双门关闭。
  • 成本提示：500k 是天花板不是均值 —— 实测中位数仅 83k，故典型任务成本不变；仅长尾任务（如 #7 的 316k）会比旧档多用约 1.6 倍 token。
